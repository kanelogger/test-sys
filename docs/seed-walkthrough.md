## 3. 共同模型前提与不变量

前三个场景各自从同一份零进度种子初始化的独立内存状态 S0 开始：AppMeta.initializedSeedVersion 取实际 seedVersion，资源 15、计划 135、日志 0。以本地操作日 2026-09-07 推演，今日 3 项共 90 分钟，9/6 六项均 pending，进入逾期待处理。

日志中的分钟、总结和导出时间均为**推演输入，不是用户真实学习记录**。模型通过暂存候选状态、检查不变量、一次返回新状态模拟提交边界，不连接 IndexedDB，不模拟真实锁或事务调度。

每次成功转移后检查：ID 唯一；resourceId、planItemId、movedToPlanItemId 均有效；completed 恰有一条日志，其他状态无日志；日志日期等于计划日期；每条 lineage 恰一个根且根 id=lineageId，非根恰一个前驱，moved 当且仅当有后继，根可达所有节点、无环、无分叉，最多一个 pending。资源和未涉任务不变。今日分钟只计当日 pending/completed，不计 moved/skipped 或未移入今日的逾期任务。

以下表格列出变化字段；没有列出的字段逐值保留。每个场景的完整受影响实体见机器证据 `scenarios[0..3]`；前三场景的其他实体从实际种子原样保留。

## 4. 场景一：当天完成

**输入**：2026-09-07，选择 `seed-20260907-01`“软件工程与开发模型入门”，预计 30 分钟，资源 `resource-web-public`。填写 actualMinutes=32，summary=“列出四种开发模型的适用条件，仍需区分迭代与原型的交付物。”。

**操作**：今日选择任务进入记录；手动填写并确认；模型重新检查 pending 后同时创建日志和完成任务。真实实现必须在同一写事务内重读和写入，不能先单独修改任务状态。

| 实体/字段 | 前 | 后 |
| --- | --- | --- |
| PlanItem.id/date | seed-20260907-01 / 2026-09-07 | 不变 |
| status | pending | completed |
| lineageId / source / resourceId | 与种子相同 | 不变，lineageId=seed-20260907-01，source=seed |
| StudyLog | 无 | id=model-log-done-20260907，planItemId=seed-20260907-01，date=2026-09-07，actualMinutes=32，summary 如输入 |

**引用与不变量**：日志只引用该任务；date 相等；每完成项恰一日志；lineage 与资源不变。今日已计划仍是 90/90，实际 32 分钟不替换 plannedMinutes；过去六项逾期不受影响。

## 7. 场景四：备份恢复

**输入**：把前三场景作用于互不冲突的任务，得到备份源状态：15 资源、136 计划、3 日志；132 pending、3 completed、1 moved；AppMeta 为实际 seedVersion。备份字段完整为 schemaVersion、exportedAt、appMeta、settings、resources、planItems、studyLogs，不携带种子的 coverage。

模型暂取 schemaVersion=数值 1，exportedAt=2026-09-07T12:00:00.000Z（模拟时间，非执行时间）。为检验兼容历史版本，**只在模型中**假设当前随包版本为 model-only-future-version，supportedSeedVersions 同时含它和真实 v1，导入 v1 成功；不要求备份版本等于当前随包种子版本。这不是创建或发布第二份种子。

**界面反馈（预期，非已实现截图）**：校验后说明“将完整替换本地数据”并要求确认；成功后重载设置、今日、历史、记录与资源，按恢复数据展示。取消不修改；失败显示具体原因，不清空现有记录、不伪报成功。

### 失败零修改

34 类非法备份分别从同一个完整本地前态尝试恢复，全部拒绝，前后序列化 SHA-256 相等，五部分均保持原值。完整错误名称、原因与相等哈希见 scenarios[3].boundaries.invalidBackups。
